## 0.4.1: History replay without a round trip

queezz, from a laptop on the LAN: "clicking the log entries, the updates
are slow". Measured on the Pi: `/history/state/<idx>` took ~110 ms per
click because every request re-parsed the whole 2382-row `logs.csv`
(the old code did the same; the Pi is simply slow at it), and quick
successive clicks could answer out of order. The History page does not run
the 5-second live poll, so no snap-back was involved.

- `history.js` reconstructs the moment's state in the browser from the
  events list it already holds plus `/elements-state` fetched once at load
  (the same backward walk as the server's `state_at_index`); a click makes no
  request. `/history/state/<idx>` and `/history/state-at` stay for permalinks
  and PIHTI Log.
- `server.py` caches the parsed history keyed by the log file's mtime and
  size, so `/state.svg?at=`, `/history/state-at` and `/history/events` parse
  the CSV only when it changed. Test added; version 0.4.1.
- Scratch `lab start pihti-diagram --port 48934 --host 127.0.0.1` (same
  redirected roots as above): three moments clicked, 1–4 ms click-to-apply,
  zero fetches during the click, browser fills identical to the server's
  `/history/state-at` answer for all 38 configured elements, console clean.
  Stopped as a tree, 48934 free. queezz's own `lab pihti-diagram` was running
  on 4186 during this check and was not touched.
